# Delivery workflow

What agents do on their own in Winnies, and what waits for the human. The path is ADR-0002: ticket branch → PR → `redesign`, and `redesign` → `main` once, as v1.0.0.

The shape comes from the compies repository, where it grew out of ten retros; rules marked "(compies)" are carried over with their reason, and a Winnies `/retro` replaces them as this project learns its own.

## Branches and merges

- **Ticket branches**: push freely. Name them `<type>/<issue#>-<slug>`; the integration branch of a spec is `spec/<issue#>-<slug>`.
- **Into `redesign`**: open the PR, then set auto-merge yourself, without asking, and move on: `gh pr merge <n> --auto --merge`. GitHub merges once `check`, `attribution`, `api-tests` and `e2e` are green.
  - Auto-merge is on for the repository (`allow_auto_merge`). A PR that is green, up to date with its base, and still open two minutes after its last check finished is merged by you directly, without asking: `gh pr merge <n> --merge` (spec #219, A8).
  - `node scripts/deploy-wait.mjs <n> --until-done`, run in the background, waits for the merge and then for the deployment of the merge commit (§ Issues). It exits 3 when the two-minute rule above applies, and 1 with what to do when the PR is red, a draft, in conflict or behind its base.
- **Into `main`**: open the PR yourself; merging it is the human's. That covers every hotfix and the 1.0.0 release. Once CI is green, hand the human `! gh pr merge <n> --merge`. A hotfix is merged forward into `redesign` after it lands.
- **Branch protection and repo settings are the human's.** `main` and `redesign` require the checks `check`, `attribution`, `api-tests` and `e2e`, admins included. The auto-mode classifier refuses an agent's call to change branch protection (tried 2026-11-10), so hand the human the command.
- **Subagents** hand their work back; the orchestrating session does every merge (`docs/agents/subagents.md`).
- A PR body is written with the `pr` skill and carries no attribution (CLAUDE.md § Attribution). A spec's integration PR opens as a draft after the first merge, with a stub body: one sentence and the `Closes` lines. It stays a stub until the PR is marked ready; then its body is written once, from the issues' records and against the final tip, and keeps the `Closes` lines. Per-ticket records live on the issues (Safety net: a body rewritten after each merge was still stale at the Spec review).

## Database migrations

Run drizzle-kit migrations on local and test databases yourself. A merge into `redesign` migrates the staging database: the Vercel build runs `pnpm db:migrate && pnpm build` (`vercel.json`, README § Deployment). A failed migration fails the deploy and the previous deployment keeps serving, so the ticket is not verified (§ Issues). Production follows at 1.0.0, when `redesign` carries `vercel.json` into `main`; until then `main` builds without a migration. A migration that reaches production does so through a merge into `main`, which is the human's; the PR that carries one says so in its first line. An agent holds no database credential, for staging or production: one that reaches a transcript gets rotated.

## Issues

- **Comments are your job.** Record what later tickets will need: decisions, deviations, verification results. A decision the human makes in chat is posted on its issue before the work goes on.
- **Verify on staging, then close.** Staging is the Vercel deployment of `redesign`, `https://staging.winnies.christried.me` (ADR-0005). Once a ticket is merged into `redesign` (a ticket on an integration branch: once its integration PR is) and the deployment of that merge commit is Ready, check the ticket against its acceptance criteria and Manual QA steps there, not only in CI. `node scripts/deploy-wait.mjs <n>` says when the deployment is Ready. A failed deployment, a failed migration included, leaves the previous one serving: the ticket is not verified, so read the build log the script points to and say so on the ticket. Post the result as a comment and close the issue yourself. `Closes #n` closes an issue only on a merge into `main`, so a ticket merged into `redesign` is closed by hand.
- A check that needs the human (Discord sign-in on staging, how a motion feels) is named in the comment and left to them; the ticket stays open until they answer.
- **A ticket handed over by a cloud session** has the label `needs-local-check` and a pushed branch whose last commit adds `.handoff/<issue#>.md`: the PR's title and body, the comments to post, and the checks left to do (`docs/agents/cloud.md` § Delivery). A session on the human's machine starts by listing them, `gh issue list --state open --label needs-local-check`. For each it removes the file in a commit of its own, opens the PR from the file, posts the comments, merges, does the checks, and verifies and closes the ticket as above; the label goes with the last check (the human, 2026-11-12, #269: a cloud session cannot open a PR that passes `attribution`, and a ticket's last look is the human's browser anyway).
- **Signed-in pages.** Only the human signs in with Discord. An agent checks a signed-in page as a dev Owner: `/api/dev/sign-in` signs in without Discord on `pnpm dev` and on staging, and no production build carries it (ADR-0005; it amends #195, story 17, for builds that are not production). `?as=<name>` names the dev Owner (take one of your own: the default, `owner`, is shared by every agent), `?to=<path>` says where to land, `?seed=reset` replaces that dev Owner's Winnies with the dummy set: one Winnie per Winnie state, one with 50 Challenges, one with very long names (`server/dev/dummy-winnies.ts`).
  The browser helper does it for you: `node scripts/shots.mjs <path> --out <dir> --as <name> [--seed]` signs in, opens the path at 1440 and 390 px, saves a screenshot of each to `<dir>` (a folder of your ticket in your scratchpad) and prints the tab's title and icon and the console errors; read the screenshots with the Read tool. `--signed-out` opens the path as a Viewer (a Share Link), and a path that answers with JSON or text (`api/winnies`) is printed instead of shot. It targets `pnpm dev` (start it first; the helper doesn't) at `http://localhost:3000`, or staging with `BASE_URL=https://staging.winnies.christried.me`. Write a path without its leading slash, since Git Bash rewrites `/x`; `/` needs no argument. It shoots the light appearance with reduced motion: dark mode and motion are not covered, so the comment names what the helper did not check and the walk-through takes it. The browser it drives is the e2e one (README § Tests).
- **On staging, a dev Owner's data is yours.** Create, change and delete anything a dev Owner owns without asking: its Winnies and Challenges, and a reset with `seed=reset`. A dev Owner's email ends in `@dev.winnies.invalid`. Rows of any other account, the human's included, are never touched. No agent holds a database credential for staging, so data changes go through the app as a dev Owner. The staging database (Neon `staging` branch) is kept until the human resets it: what the human set up there for a walk-through stays.
- **The bypass secret** (`VERCEL_AUTOMATION_BYPASS_SECRET`, the project's Protection Bypass for Automation) is a credential: it lets a request past staging's Vercel login. It lives in the main checkout's git-ignored `.env`, which `.worktreeinclude` copies into every agent worktree, in the Vercel project's settings, and, once the human saved it there, in the cloud environment `winnies` as a network secret no agent can read (`docs/agents/cloud.md` § Staging); `scripts/shots.mjs` is the only thing that reads it (README § Environment variables). Never print `.env`, and never put the value in a command, a file, a commit, an issue, a PR or a report. One that reaches a transcript, an issue or a report is rotated: the human makes a new one in the project's settings and runs `bash scripts/staging-wizard.sh`.
- **`scripts/shots.mjs` is the one way into staging.** The Vercel connector's `web_fetch_vercel_url` and `get_access_to_vercel_url` are denied in `.claude/settings.json`, under the names of a local and of a cloud session: each creates a share link past Vercel login that opens staging, dev sign-in included, to anyone holding it for 23 hours.

## Review, walk-through, retro

Every phase of the roadmap (one spec, one milestone) ends with these steps, in this order. A step that finds work makes tickets, fixed before the next step.

1. **Review.** Once every ticket of the phase is on the integration branch, review its diff in three `sonnet` subagents at high effort: `code-review` Standards, `code-review` Spec against the phase's spec and tickets, and `thermo-nuclear-code-quality-review` with `improve-codebase-architecture`. Each writes its report to a file in the orchestrator's scratchpad and returns at most 300 words; a `haiku` agent merges the files into `docs/reviews/review_<phase>_YYYY-MM-DD.md`. The orchestrator reads the headlines and turns what must change into tickets. (compies, retro 0.9: three full reports in the orchestrator's context cost what a whole ticket does.) Every finding ends in one of three places, which the review file's last section lists: a ticket fixed in this phase; a line in `docs/roadmap.md`, under the phase it must land in or in § Engineering backlog, naming the review; or a note. (Before R0: two "ticket for later" findings ended as notes, one of them due before the first redesign icon.)
2. **Verify.** Each ticket is verified and closed as § Issues says.
3. **Walk-through.** Open a `ready-for-human` issue "Walk-through <phase>" with a checklist built from the spec's acceptance criteria. It is a joint session: the agent presents one surface at a time on staging, the human judges it, and each finding becomes a ticket. How things look and how motion feels are the human's call; agents measure numbers.
4. **Retro.** Ask the human to run `/retro` on the phase's sessions: what the review and the walk-through caught that a check, a standard or a brief should have caught earlier. A mechanical mistake becomes a lint rule, a test or a hook; a judgement call becomes a line in `CODING_STANDARDS.md` or `docs/agents/`, with the incident that caused it.

The next phase is specced only after the retro (`docs/roadmap.md`).

## Branch hygiene

GitHub holds `main`, `redesign` and branches in active development. Before ending a work session, run `git fetch --prune` and delete the merged remote branches yourself, without asking: `git push origin --delete <branch> …`. Running the worktree cleanup below is yours the same way (the human, 2026-11-11, after the auto-mode classifier had refused both on 2026-11-10).

Agent worktrees go with `node scripts/worktree-clean.mjs [--unlocked] [<agent ids>]`, run in the background (a worktree with `node_modules` takes minutes). It removes a worktree that is named on the command line, or that is locked by a Claude process that no longer runs, the session of an agent that has ended. A worktree that is not locked and not named stays, listed with the reason; `--unlocked` removes those too, for the end of a phase. A worktree whose session still runs stays until it is named. Whatever the rule, it keeps a worktree with uncommitted changes, an unpushed commit or a process running in it, and says why. Name an implementer's agent only once its ticket is verified: cleaned earlier, a failed check needs a fresh implementer to rebuild the context (compies, 2026-11-09). `--dry-run` prints what it would do and changes nothing.
