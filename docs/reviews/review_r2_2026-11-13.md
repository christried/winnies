### Q1. A `bare` variant of `UiTextInput` is the better seam for the counter (later; before the R3 counter swap)

- **Verdict:** Counter: yes. InlineEdit: no.
- **Where:** `app/components/ui/counter.vue:168-183` throws away almost everything `UiTextInput` draws. It sets `w-auto!` on the root; inside, it overrides height, width, radius, background, padding, alignment, text colour and `box-shadow` (`[&_input]:[box-shadow:none]!`), and re-draws the focus ring. It passes `hide-label` and no message or counter, so the label row, message row and wrapper never render. The `!` is a symptom: `text-input.vue:170` puts the well chrome (shadow, hover ring, focus ring, `aria-invalid` ring) in the one class string shared by all three variants, and the state variants out-specify any single-class override. The counter also depends on there being an `<input>` inside it (`[&_input]`). What it wants from the component is the number behaviour (`typed`/`shown` and `numberValue`, which keeps `1.0` while the user types towards `1.05`), not the well.
- **Fix:** split the class string into BASE, WELL (the pill chrome) and the per-variant size, as `button.vue` does with `VARIANT_CLASSES` and `SIZE_CLASSES`. Add `variant="bare"`, which gets BASE only: no well, no rings, its own focus outline. The counter then loses `w-auto!`, the `[&_input]:` list and the `!`. Its baselines are re-recorded. The risk is visual, not behavioural; the counter's stories cover it. Open the ticket now; do it before the R3 swap of `counter-pill.vue`.
- **Keep:** `UiInlineEdit` overrides one property (`[&_input]:bg-surface-raised`, `inline-edit.vue:171`) at a specificity that wins without `!`. The handoff gives an editing title a raised fill. If a second consumer wants a raised `inline` well, add a `raised` boolean to the text input then.

### Q4. `UiIconButton` wraps every button in `UiTooltip`: `aria-describedby` and the trigger lookup (must fix in R2)

Two problems, both fixed in R2, both in `tooltip.vue`.

- **4a. Screen-reader output** (needs an AT repro to size). Every icon button gets `aria-label="Delete"` and `aria-describedby` pointing at a `role="tooltip"` element whose text is also "Delete". A node referenced by `aria-describedby` contributes its text even while hidden, so the description exists all the time. Expect "Delete, button, Delete" on each of the ~150 Workspace buttons; some engines or screen readers may drop a description identical to the name. This is not verifiable without a repro. `07-accessibility.md:83` asks only for "aria-label + tooltip".
  - **Fix:** a `describes` prop on `UiTooltip`, default true, for the future `data-tip` case where the bubble carries text the trigger lacks. `UiIconButton` passes `:describes="false"`. The trigger then omits `aria-describedby`, and the bubble gets `aria-hidden="true"`, because the name already carries the text. Update `tooltip.stories.ts:94` and `:644`, which read the popover through `aria-describedby`.
- **4b. A caller's own `aria-describedby`** (concrete bug). `icon-button.vue:57` does `mergeProps(trigger, attrs)`: for a non-class, non-style, non-`on*` key the later source wins, so a caller's `aria-describedby` silently replaces the tooltip's. `tooltip.vue:44` then finds its trigger with `document.querySelector('[aria-describedby="${id}"]')`, which returns null. On the fixed-placement path `place()` returns early, `fixed` stays undefined, and the style falls back to the anchored branch; in a browser that cannot anchor, the bubble sits at its static position. In anchoring browsers it still works, because `anchor-name` is joined by name. No caller passes `aria-describedby` today, which is why no test caught it.
  - **Fix:** stop finding the trigger through a DOM attribute. `onPointerenter` and `onFocus` already receive `event.currentTarget`; store it in a local `triggerEl` and use that in `place()`. This also drops the global `document.querySelector` and the reliance on the id being unique. Add a story where the trigger carries its own `aria-describedby`.
- **4c. The support check** (related, same file). `anchorPositioningSupported()` (`utils/tooltip.ts:19`) tests `anchor-name`, but the component's style uses `position-area` and `position-try-fallbacks`. `menu.vue:158` tests `position-area`. Chromium shipped `anchor-name` before `position-area` (it was `inset-area` first), so a version window gets the anchored branch with no `position-area`.
  - **Fix:** test `position-area` (confirm against MDN compatibility data), or reuse the menu's check. Both components should share one check (Q7).

### Q8. Toast live-region semantics (later, after an AT repro)

- **Where:** the old `toast-region.vue` was `aria-live="polite"`. `UiToastStack` is a plain `div`, and each `UiToast` carries `role="status"` or `role="alert"` and is inserted already filled. A live region has to exist before its content changes, so a `status` that arrives with its content is announced unreliably in some screen readers; `alert` is safer. Each toast also contains a `UiIconButton` "Dismiss", so a `role="alert"` card holds a tooltip popover; when the bubble shows, the text it reveals sits inside a live region.
- **Fix (suggested):** make the stack the live region (`role="region" aria-label="Notifications" aria-live="polite"`) and keep `alert` for errors; mount the tooltip outside the card or mark it `aria-hidden` (Q4a does that). This is a behaviour change against ADR-0001, so name it in the PR.

### Q9. `UiCounter`'s root uses `aria-disabled` on a role-less `div` (later)

- **Where:** `counter.vue:132`. ARIA 1.2 deprecates `aria-disabled` as a global attribute and does not allow it on a generic role. The comment says it is there so axe sees the dimmed "/ target" as disabled.
- **Fix:** `role="group"` with `:aria-label="countLabel"`. It is valid ARIA, and it gives a screen-reader user the widget's context: today a user hears only "Decrease X" and "Increase X" as separate controls.
