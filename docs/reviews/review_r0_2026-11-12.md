### Findings

#### 1. The motion cookie is seeded from the account and then outranks it for a year (judgement call) — ticket for later

- **Where:** `app/plugins/motion.ts:9-13` (`default: () => user.value?.reduceMotion`), read at `:16`; the same pattern at `app/plugins/theme.ts:8-12`.
- **Problem:** `useCookie`'s `default` is written to the response when no cookie came in (`node_modules/nuxt/dist/app/composables/cookie.js`, `writeFinalCookieValue`: it writes when `cookie.value` differs from `cookies[name]`). So the first signed-in visit in a browser stores `winnies-reduce-motion=false` for a year, and the computed at `:16` lets a readable cookie beat the account. Story 12 ("stored on my account so it follows me to every browser I sign in on") then fails for any browser visited before the preference changed: turn it on in browser B, browser A keeps the seeded `false`. `motion.spec.ts:120` ("the cookie wins over the account") pins the precedence, not the seeding. No user can reach this today (no switch, no caller of the endpoint), which is why it is not a blocker.
- **Restructuring:** drop `default` from `useCookie` in the motion plugin. The computed already falls back to `user.value?.reduceMotion`, so a browser with no cookie follows the account and a cookie exists only after the switch writes cookie and account together. Add one e2e case: account true, cookie never set, fresh browser reduced; then account changed, the other browser follows. Theme has the same seeding from before this phase (story 5 is met by the fallback too), so decide once for both.
- **Verdict:** ticket for later, scheduled before the Reduce motion switch lands with the header's theme popover (R3).

#### 2. The deviation block's tests depend on the one live block, and nothing pins its copied values (judgement call) — ticket for later

- **Where:** `scripts/handoff-sync.test.mjs:254,262,271` (hard-coded `#268` markers); `docs/design-deviations.md:3,7` versus the test; `app/assets/css/winnies-tokens.css` end of file.
- **Problem:** (a) The entry says the block goes once the handoff takes it in. Removing it makes three tests fail, because `plant()` asserts that its regex matched `#268`. The mechanism's end of life breaks its own tests. (b) The block restates 5 composites "with the value text of its theme block"; nothing compares that text with the theme blocks, and the e2e (`tokens.spec.ts:232-258`) checks only lips and `--btn-text`. When the next handoff re-sync changes a shadow in the theme block, the dialect copy goes stale silently. (c) The doc says "at the very end"; the test accepts a block anywhere, and no check ties each `#N` block to an entry in `design-deviations.md`.
- **Restructuring:** plant a synthetic block into a copy of the text (as the "other file" case at `:277` already does) so the tests own their fixture. Add one assertion in `differences()`: for each custom property inside a block that is also declared outside, the whitespace-normalised value text is equal. Add: every `#N` marker has a `## … · #N ·` heading in the doc and the reverse.
- **Verdict:** ticket for later, before the first token re-sync (R2 at the latest).

#### 3. A story id in `only` or `skip` is never checked against a story, and nothing checks the baselines on disk — ticket for later

- **Where:** `.storybook/visual-variants.ts:146,160,165` (string ids), `isShot` at `:170`; `.storybook/vitest.setup.ts:213`.
- **Problem:** the variant table is the decision about what is compared, and the whole suite's value is that decision. A renamed story id turns `only: ["tokens-switches--default"]` into "shoot nothing" and a `skip` into "shoot everything", both silently. A story newly skipped leaves its old PNG on disk, uncompared, forever. Today the 35 PNGs equal the table (checked by count); no test says so. The note "compared byte for byte to decide it (#265)" is a one-time manual act.
- **Restructuring:** one test next to `visual-env.test.mjs` (it is a pure module): list `stories/**/*.stories.ts` (title slug + export name, as Storybook ids), assert every `only`/`skip` id is one, and that `stories/__screenshots__/<variant>/*.png` equals exactly what `isShot` says is shot. It fails when a baseline is orphaned or missing before CI does.
- **Verdict:** ticket for later, before the first component story (R2).

### Deepening candidates

Checked against `GLOSSARY.md` and ADR-0001 to 0005; none contradicts an ADR.

**A. Preference (a user's saved choice that renders as an attribute on the server). Worth exploring, when the third one (the Overlay preset) is specced.**

- Files: `shared/constants.ts`, `shared/utils/{theme,motion}.ts`, `shared/schemas/user.ts`, `app/plugins/{theme,motion}.ts`, `server/db/queries/user.ts`, `server/api/user/{theme,motion}.put.ts`, `server/utils/{auth,schemas}.ts`.
- Problem: a preference is spread over eight files in six layers and reappears in each copy. The interface of every piece is as wide as its body (shallow). The deletion test: deleting `updateUserReduceMotion` re-creates `updateUserTheme`, so the complexity is repeated, not concentrated. Finding 1 is a bug that exists in both copies because there is no one place that owns "cookie against account".
- Solution: one module that owns a preference's cookie, parse, account fallback and save, behind an interface of name, schema and attribute. Theme and motion become two adapters; a third makes the seam real (one adapter is hypothetical, two is the minimum, three is where it pays).
- Benefits: locality for the cookie-versus-account rule (the rule gets one test instead of two e2e pins); leverage for the Overlay preset and any later skin preference.
- Strength: Worth exploring. Speculative before the third preference.

**B. The document switches (theme on `<html>`, dialect on `<body>`, motion on `<html>`). Speculative.**

- Files: finding 13's list.
- Problem: seven places state where each attribute goes, so a bug about "which element" (the #268 composite issue was exactly that) has no one place to be fixed or tested.
- Solution: one table in `shared/` (switch name, element, attribute, allowed values) that the plugins, `useDialect`, the Storybook decorator, the variants and the e2e `switchAttributes` all read.
- Benefits: leverage across the app, Storybook and the tests; locality for adding a value. Cost: the plugins have per-switch logic (system theme, cookie parsing) that stays outside the table, so the table would not own behaviour, only names. That is why it is speculative.
- Strength: Speculative.

**C. The Handoff copy (`handoff-sync.test.mjs` with the deviation mechanism). Worth exploring after finding 2.**

- Problem: the module is already deep (one pair list, one verdict) but its two ways of walking the files (finding 11) and its tests tied to one live block (finding 2) mean a deviation is added by hand in three places (CSS block, doc entry, marker rules).
- Solution: a pure `deviations(text)` returning blocks with their issue number, used by the sync test, the doc check and a Storybook "what deviates" readout.
- Benefits: one parser, one test surface; the block's end of life becomes a one-line deletion.
- Strength: Worth exploring.

**D. The screenshot variant table. Strong, but small (finding 3).**

- Files: `.storybook/visual-variants.ts`, `.storybook/vitest.setup.ts`, `stories/__screenshots__/`.
- Problem: `isShot` and the PNG directory both describe what is compared, and only CI joins them (and only for a missing file).
- Solution: make the table the single source, and add the one test that derives the expected PNG set from it.
- Benefits: locality for "what is compared"; the suite stops being able to lose coverage without a red test.
- Strength: Strong.
