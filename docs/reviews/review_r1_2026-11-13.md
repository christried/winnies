### 1. #337: at 1000 ms a minute rollover's last slot is shortened, against the ticket's second criterion (spec contradicted) — must fix in this phase

- Where: `app/utils/motion/engine.ts:320` (`Math.max(1, Math.min(dur, iv * 0.95 - delay))`); pinned by `app/utils/motion/ticks.test.ts` "at 1000 ms a minute rollover's last slot gives up 20 ms to end at 0.95 of the interval" (`digits[5]` duration 700, not 720).
- Why: #337's criterion 2 says "At the product's 1000 ms interval, a second tick and a minute rollover play exactly as today: the same delays, durations and keyframes. The hour rollover keeps its stagger and its keyframes; only the durations of the slots that would overrun get shorter." The ticket's body, the brief's table and the handoff's "Open for the human 1" all say the minute fits ("250 ms plus 720 ms ends at 970 ms"). It does not fit the code's own rule: criterion 1 and the engine clamp to 95% (950 ms), so 970 ms is over, and slot 5 of every minute rollover loses 20 ms (and the Total's and each row's alike, since the rule applies to every rollover). ## Quality and architecture

Range `e518d06...origin/fix/337-rollover-overlap` (tip `6fa7275`: the integration branch `spec/294-r1-engine` at `28d2936` plus #337's fix), without `pnpm-lock.yaml`; #337's missing entry in `docs/design-deviations.md` is not a finding. Method: `thermo-nuclear-code-quality-review`, then step 1 of `improve-codebase-architecture` with the `codebase-design` vocabulary (module, interface, depth, seam, adapter, leverage, locality). Read-only, from the diff, the code, the issues and CI (runs 43380700338 `CI` and 43380700250 `Attribution` on the tip: success). No builds, no repros, no sub-agents. Most weight: the surface clock, the engine's lifecycle (`watch`, `subscribe`, `loops`), the loop host, the transition hooks, `surface.ts`'s quieting, and what the first R2 to R4 consumers will have to remember. ADR-0003's near-verbatim port is respected: a smell that is the reference's own shape is at most a note, and the Standards report's findings are cited by number, not repeated.

Checked and clean:

- Listener, observer and timer cleanup on the paths that exist. `createSurfaceClock.stop()` clears the one timer and the visibility listener; `fire()` re-arms in a `finally` only while `running`, and `arm()` clears before it sets, so a listener that calls `stop()` or `stop()` then `start()` cannot leave two chains. `provideSurfaceClock` and `provideWinniesMotion` start in `onMounted` (never on the server) and stop or dispose in `onBeforeUnmount`; the clock stops first, then the motion instance, and every layout registers the clock first so it starts first. `createSurfaceMotion.dispose()` stops the media listener and the `MutationObserver` (`env.ts:142-155`, `disconnect`), stops the loops, cancels what runs and empties the layer. `refreshOnReturn` removes both listeners. The loop host attaches its tab listener and engine subscription on the first element and detaches on the last, and `loop-sync.test.ts` counts both, a deliberate guard for the Overlay.
- The clock's arithmetic. Every delay is taken from the source's own second boundary, so a `sync()` that moves the offset corrects at the next tick, a late timer shortens the next delay, an early timer re-arms, a source that goes back becomes the new reference, and a frozen source reports nothing. Beats are measured against the previous reading, so a long gap reports one beat of the largest boundary crossed. The visibility handler reads the source at once on return instead of trusting a throttled timer.
- Ordering of the clock, the engine and the loop host. `now` and `beat` are set before the listeners run, listeners run on a copy of the set, and a throwing listener cannot break the chain. On first render a child's `v-loop` mounts before the layout's `start()`: #335's `announce` makes the first refresh tell the host, which rebuilds a loop whose `loopKey` changed from the defaults. A dialect attribute that `useHead` writes after the layout is set up is caught by the observer, not by the order of calls. When reduced motion arrives, the engine's `stopLoops`, the host's `onEngine` and `quiet()` do not depend on the order their subscribers were added, and the first announce runs before `quiet` is subscribed, which is harmless at load.
- SSR and hydration. `engine.ts`, `env.ts`, `loop-sync.ts` and the composables touch no browser global at import; every `browserEnv` member answers for the server; `v-loop` has no server hook, so the server HTML is identical with and without it; the layer is static; the clock's reading rides `useState("surface:now")`, so the server's value hydrates, and the first change comes in `onMounted`. Nothing at module level holds per-request state: `hosts` is a `WeakMap` keyed by the engine, and the inert fallbacks build a fresh instance per call.
- Reduced-motion paths. The engine reads the config, the media query and `<html data-motion>` live on every call, so gating holds before `watch()` and while a token is stale. `quiet()` cancels only running or paused plain animations and leaves a finished `fill: forwards` one alone, so an exited row does not snap back; the particles are cancelled and then removed by hand, because a cancelled animation never fires `onfinish`. `createTransitionHooks` settles through `Promise.allSettled`, so a document-wide cancel ends the transition instead of hanging it, and it releases a previous leave's held end state on a new enter.
- \#337's fix. `delay + duration` is now clamped to `iv * 0.95` with delay at most `iv * 0.3`, so the duration never falls below `0.65 * iv`; below 120 ms every beat takes the plain per-second shape before this code is reached, and `Math.max(1, …)` keeps it positive. The well's animation, the burst and the cue are not delayed, so nothing else moves.
- `useMotionTransition` is correct about `getAnimations({ subtree: true })`: a child's `v-loop` mounts before the transition's `onEnter`, so loops are in the `before` set and the hook does not wait for an infinite animation.
- The recorder (`tests/support/fake-motion.ts`) and the browser are two adapters of the same seam (the DOM's `animate`, `getBoundingClientRect`, `closest`, `children`, `ownerDocument`), and `MotionEnv` and `LoopEnv` are two more. These are real seams, not hypothetical ones, and the node tests drive the real engine through them.

#### 1. Beats and recipes carry on in a hidden document, and nothing at the seam says so — ticket for later (R3 Workspace, with a repro ticket first)

- **Where:** `app/composables/use-surface-clock.ts:108-130` (`fire` keeps ticking while hidden, pinned by "a hidden tab keeps ticking" in `use-surface-clock.test.ts:282`); `app/utils/motion/engine.ts:84-95` (`m.on` gates on tier, reduced motion and the ambient pause, not on `document.hidden`); `engine.ts:261`, `:431` (`m.tick`, `m.beat`), `:208`, `:236` (bursts); `app/composables/use-motion-transition.ts:415` (`done` waits for `finished`, with no timeout).
- **Problem:** the clock is deliberately awake in a hidden tab (the title, #304) and publishes `hidden`, but the engine has no idea. Today `onBeat` has no caller in `app/`, so nothing is wrong yet; R3's timer digits are the first, and each beat creates one animation per slot. A hidden document renders no frames, and what that does to Web Animations (are new animations pending until the next frame, does `finished` resolve late, do they pile up for hours on a tab left behind a window, do all of them play at once on return) is a browser fact that no unit test here can show. Two related effects are readable from the code: a beat that fires on return reports the boundary crossed while hidden, so a rollover tick, burst and chime can replay for a minute or hour boundary that ended long ago; and an enter or leave started while hidden has no fallback if `finished` stalls, so Vue's `done` waits. Then decide where the rule lives: the cheap, central answer is that `m.tick`, `m.beat` and `burst` skip while the document is hidden (the engine already has an `env`), and the clock marks a beat that fires on return as late. Do not ask each R3 component to remember `clock.hidden`.
- **Verdict:** ticket for later, R3 Workspace: the repro first, before the timer's tick ticket.

#### 2. A beat subscription is a bare unsubscribe function, so each R3 and R4 consumer must remember it — ticket for later (R3 Workspace)

- **Where:** `use-surface-clock.ts:31`, `:151-156` (`onBeat` returns a closure); `engine.ts:114-119` (`m.subscribe`, the same shape); compare `use-loop-directive.ts:324-330`, where the directive's `unmounted` does the releasing.
